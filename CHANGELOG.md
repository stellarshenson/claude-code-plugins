### Added

- **svg-infographics** - a plugin agent, `svg-infographics:svg-builder`, is the builder on both dispatch planes: the umbrella skill forks onto it and `/svg-infographics:create` dispatches one per graphic. - **svg-infographics** - `background --type dotsea`, a sea of dots: a square or honeycomb lattice on a pinhole ground plane rolling toward a hazy horizon, rows compressing as 1/depth, columns converging on the vanishing point, radius and opacity falling with depth so the field dissolves a little before the horizon, and a layered-sine swell lifting the rows into a slow wave. `--horizon`, `--fade-rate`, `--opacity`, `--waviness` (`calm` / `moderate` / `rough` or a float), `--connections` (faint mesh lines - a square grid for dots, hexagon outlines for hexagons - off by default) and `--shape dot|hex`; `--direction` is the side the field recedes toward, `radial` from the centre outward. Each marker carries its own opacity and radius because the fade is geometry, colour stays with the caller's CSS. Built against the stackrails.ai hero plate through five measured render-compare rounds (column and row periods, ink per band, top-edge undulation); the renders and the iteration log sit under `tmp/dotsea/`
- **svg-infographics** - `examples/theme_swatch_6_stackrails.svg`, the StackRails palette as a standard theme swatch: emerald on hue-228 near-black, dark mode brand-verbatim and light mode derived (emerald-700 strokes, since emerald-500 is 2.5:1 on white), semantic warn / risk / info classes, the rails-and-dots logo mark; listed in the examples index, the theme skill and the theme command
- **svg-infographics** - `mesh` and `wireframe`: real objects in an infographic. `mesh` carries a bundled catalogue of the 1,254 CC0 props on thebasemesh.com (30 categories - urban, home, decorative, industrial, architectural, kitchen, tools, furniture, buildings; no people, no trees, two whole vehicles), crawled from the site's asset sitemap and each page's embedded record, and searched offline by a standard-library BM25 with fuzzy tokens (a one-letter typo still matches, a run-together compound matches on its leading word; a name hit outweighs a category hit): `search`, `list`, `categories`, `fetch` (the OBJ unpacked from the archive in memory into `~/.cache/svg-infographics/meshes/<slug>.obj`, never downloaded twice), `path` and `index --rebuild`. `wireframe --model <slug|file.obj>` projects the mesh - quads kept as quads, yaw / pitch / roll / fov / fit - and prints an unstyled `<g class="wireframe" data-model data-bbox>` fragment: `wire` draws every unique edge once with opacity falling from 0.95 to 0.18 with depth, `hidden` culls back faces by Newell normal and paints the rest far to near as filled polygons so nearer faces cover the lines behind them (a `.wireframe polygon { fill }` rule supplies the plate colour in each mode). No element carries a `stroke` or a `fill`; colour is the caller's. The catalogue JSON ships as package data (the `.gitignore` `data/` rule gets a negation for it); `tests/test_mesh.py` and `tests/test_wireframe.py` add 50 mutation-checked tests; `rules/shapes.md`, `references/tools.md`, the create and beautify skills and the README carry the placement rules
- **datascience** - `hypothesis-tools` grows from four read-only queries into the working surface of a hypothesis campaign, shaped by five real ledgers across four projects (docdistance, knowledge-graph-foundry, sci-demographic-collapse, gpu-benchmark - up to 6,432 lines and 554 hypotheses). Parsing: a third declaration shape (a row of an at-a-glance table whose header names claim/verdict columns - one store declares 478 hypotheses of which the previous parser saw 46), and open-vocabulary verdict reading (case, emphasis, dated qualifiers and hyphen variants fold to canonical; a ledger-grown label like `SUPPORTED` is read as written, warned once aggregated; only an unreadable verdict errors) - the five ledgers went from 867 check errors to 18, all on genuinely mixed verdicts. Writes, append-only like the ledger itself: `register` lands a pre-registered hypothesis at the next free ordinal and verifies it parses back - a field name given twice, or one opening with a hypothesis id, is refused before the file is touched, as is any `result` or `field` line no reader would match (a `*` in the label; ACC-HYPTL-119..121), `result` / `verdict` / `log-event` record outcomes (Result immutable - a re-run needs a qualifier; one verdict ever - a flip is a new round). Reporting: `report` renders batches by verdict labels, `values <quantity>` returns every reading of one measured number (`theta(0.08) = 0.7644` off line 4317 of 6,432) so the file is never read end to end (ACC-HYPTL-93..103). Authorship is the `project-management` toolkit's, unchanged, so one handle is one person across a project's ledgers, criteria and defects: a `## Authors` roster written by `hypothesis-tools author`, `--author @xx` required on every write and refused when the handle is not on the roster, and each write appending its own dated `log:` line naming it - registered, result recorded, verdict recorded, field added - so who recorded what survives the session. `field` adds a name the template does not list, or replaces one already recorded with `--update`, keeping the label and its qualifier: the five real ledgers carry hundreds of field names of their own (`Grounding`, `Persona`, `Status`), so `check` never flags an unknown name - it errors only on a log handle nobody is rostered for, and warns once, aggregated, on unauthored lines the ledgers already had; `list --author` names the registrant and never the first writer (ACC-HYPTL-104..109). `check` reads a canonical label followed by scoping prose (`Refuted on the replacement bar;`, `**Refuted** as an order measure (...)`) as that label - the last three errors standing on the two docdistance ledgers - counts unrun hypotheses (neither Result nor Verdict) in its summary line instead of warning once per block, and reports missing fields as one line per field naming the ids. The template declares a batch's shared guardrails once in the batch's opening line rather than in every block
- **datascience** - `hypothesis-tools lock` / `unlock`: several hands on one ledger can pick up the same hypothesis, so a hypothesis now carries the `project-management` toolkit's soft lock, unchanged in its rules - `- lock: <ISO 8601 UTC stamp> @xx [note]` as the block's first bullet, any rostered author, 24 hours by default, `--hours` / `--until` for another span, a courtesy signal and never a gate. A write by another author warns once on stderr and lands unchanged; every write first drops the locks whose stamp is past, silently; `verdict` drops the hypothesis's lock whatever its expiry and `lock` refuses a verdicted hypothesis; taking or clearing someone else's active lock is called out as a `TRANSFER` and records `taken over from @yy`; `list`, `show` and `report` open with `N hypothesis(es) currently worked on: ...` on stderr so the pick is informed, `list --locked` / `--locked-by @xx` filter on it and `--json` carries `lock` as `{by, until, note}` or `null`; `check` errors on a malformed or duplicate lock line and warns on an expired one or one sitting on a verdicted hypothesis. Locking is never logged. The hypothesis skill, its ledger-queries reference and the `/datascience:hypothesis` command state locking as a standing default: lock what you pick up, ask before writing to a hypothesis somebody else holds (ACC-HYPTL-124..131)
- **project-management** - every item id now carries a required item code: `ACC-SVG-1-CONSTRUCT`, `DEF-JRNL-1-PARSER`. `add --code` is required and appends it; the id is read from the right, so a trailing all-digit segment is still the regression ordinal (`DEF-JRNL-1-PARSER-1`), a base id such as `DEF-JRNL-1` resolves to the coded item in every link, `--id` and reader, and `edit`, `amend` and `reopen` keep the code. The query surfaces follow: `list --columns code`, a `--code` filter on `report`, `list`, `pivot`, `search` and `coverage`, `code` in every `--json` item record, `pivot --rows code` with uncoded last, and search indexing both the code and the base id. `check` errors on a malformed code and warns on an id that carries none. `add`'s nested-item hint in `upgrade` now names `--code` too. An existing document migrates with `migrate-codes FILE --map MAPPING --author @xx`, which appends the code each `BASE-ID CODE` line names before any regression ordinal, logs one `coded CODE` line per changed item, is idempotent, and reports the items that carry no code and are not named by the mapping, and the mapping ids that match no item; `rename-code FILE --id ID --code NEW --author @xx` replaces a wrong code and rewrites every `related`, `blocked-by`, `overrides` and `overridden-by` line in the scanned trackers that names the old full id. The mapping format, the order of operations and the checks are in the skill's `references/codes.md`
- **project-management** - one registered explanation per item, and it keeps its history: `- mechanism: <stamp> @xx <text>` on a criterion says how it is meant to work, `- root-cause: <stamp> @xx <text>` on a defect says why it happens. A second write puts the new record ABOVE the previous one and keeps it, so on a hunt that runs for days the theory disproved on Tuesday is still readable on Friday and nobody explores that dead end twice; `--update` rewrites the newest record instead, for a rewording of an unchanged theory. The top record is what every query reports, `--grep` and `search` read the superseded ones too, and `--json` carries the whole history under `causes`. Written by `pm-tools mechanism` / `pm-tools root-cause`, or by `add --mechanism` / `add --root-cause` at filing time; refused on the other discipline; never logged, because the record carries its own stamp and author (ACC-PMWHY-82..90)
- **project-management** - the item code is written wherever an id is. `check` warns on a base id written on an item's line or any sub-line except `log:` (append-only history) and `attachment:` (a path), and names the full id to write: `DEF-ADVR-40 has no code; write DEF-ADVR-40-MATERIALITY`; a base id plus ordinal (`DEF-LNCH-3-1`) names the coded regression, and an id inside a file path or naming no item stays silent. A warning, never an error. `relate` writes a base id given on `--related`, `--blocked-by`, `--overrides` or `--overridden-by` as the full id it names, keeps the text around it as typed and prints the code it added (`DEF-LNCH-2 -> DEF-LNCH-2-SPLASH, added code SPLASH`)
- **project-management** - `rename-category FILE --category OLD --to NEW [--name NAME] --author @xx` renames a category code across the store, FILE and every tracker beside it: in each tracker of FILE's prefix the `##` headings with code OLD and the ids with segment OLD, number, item code and ordinal kept, and in every tracker each mention of a renamed id, full id to full id and base id to base id. An id naming no item stays; an id inside a file path outside a relation line and every `attachment:` line stay as written and are listed on stderr. Every check runs before the first write, so a refusal writes nothing. A rerun of the same command after a git merge finishes the rename: it renames the items the other branch added with segment OLD and rewrites its links to the old ids, once no heading of FILE's prefix carries OLD and FILE's NEW heading holds the earlier rename's record, and refuses an id one would take that already exists (DEF-PMGT-86-MERGE-RENAME). It is the one change to an id once assigned (ACC-PMCAT-222..250)
- **project-management** - tracker and category logs: the item log line without indent, in the preamble for a change to the whole file and under the category description for a change to one category. `add` creating a category and `describe` write a category record, `migrate-codes` coding an item and `upgrade --apply` changing the file with `--author` on the roster write a tracker record, `rename-category` writes both; a command that changes nothing writes none. `check` validates their stamps and handles as on an item log line, and a log line is never read as the description (ACC-PMLOG-207..221)
- **project-management** - category notes: every non-blank prose line after a category's description is a note, numbered from 1 in file order past blank, fenced and category log lines. `describe --append TEXT` adds the last note after the last prose line, `describe --note N --text TEXT` changes note N, keeping the leading whitespace of its line, and `describe --note N --remove` removes its line alone; each writes one category record (`added note "TEXT"`, `changed note N "OLD" -> "NEW"`, `removed note N "OLD"`), and the same text writes nothing.
